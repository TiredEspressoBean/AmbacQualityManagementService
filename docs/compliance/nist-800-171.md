# NIST SP 800-171

Protecting Controlled Unclassified Information (CUI) in nonfederal systems.

## Overview

| Framework | Version mapped | What this page is |
|-----------|----------------|-------------------|
| NIST SP 800-171 | **Rev 2** | A control-by-control map, not a readiness score |

!!! warning "Revision 3 exists, and this page deliberately still maps Revision 2"
    **NIST published SP 800-171 Revision 3 in May 2024.** It is a substantial
    change, not a refresh: the control count drops from **110 to 97**, three new
    families appear, 33 controls are withdrawn, 19 are new and 46 changed
    significantly. It also introduces **Organization-Defined Parameters** — 49 of
    them — where values you choose become part of the requirement. The companion
    assessment guide went the other way, from 320 assessment objectives to 422.

    This page stays on Rev 2 because **CMMC Level 2 is the same control set**, and
    which revision CMMC requires is the part currently in motion. Mapping Rev 3
    here while [CMMC](cmmc.md) maps Rev 2 would leave two pages describing the same
    controls and disagreeing about how many there are.

    **So check which revision your contract actually invokes** — the DFARS clause
    and your CMMC obligations decide that, not this page. Where they call for Rev 3,
    treat this mapping as a starting point and expect the control identifiers to
    move. The *capabilities* described in each row do not change; only the numbering
    and grouping around them do.

!!! info "What this page covers"
    **You** are the assessed party, and there is no readiness percentage to
    quote. This page lists only the controls where the software is the
    mechanism, or part of it, and says what it does. Controls that live in
    your organisation, identity provider or hosting are listed once, under
    [Organisation and hosting responsibilities](#organisation-and-hosting-responsibilities).
    For the same controls framed by CMMC domain, see [CMMC](cmmc.md).

NIST 800-171 provides security requirements for protecting CUI when processed, stored, or transmitted by nonfederal organizations. It contains 110 security requirements across 14 families.

## Applicability

NIST 800-171 applies when you:
- Handle Controlled Unclassified Information (CUI)
- Contract with federal agencies (especially DoD)
- Are in the defense industrial base supply chain
- Process data subject to DFARS 252.204-7012

## 3.1 Access Control

| Control | Requirement | | Implementation |
|---------|-------------|---|----------------|
| 3.1.1 | Limit system access to authorized users | ✅ | `DEFAULT_PERMISSION_CLASSES = [IsAuthenticated, TenantAccessPermission, TenantModelPermissions]`; the session and token authenticators refuse a user who asks for a tenant they do not belong to |
| 3.1.2 | Limit access to authorized functions | ✅ | 15 role presets (`GROUP_PRESETS`); `TenantModelPermissions` maps HTTP methods to view/add/change/delete permissions, with per-action gates on the viewsets; `TenantScopedMixin` filters every queryset to the tenant and the user |
| 3.1.3 | Control the flow of CUI | ✅ | Documents carry a `classification` (Public, Internal, Confidential, Restricted, Secret), filtered by `for_classification()`; ITAR- and EAR-flagged documents, part types and parts are filtered by `for_export_control()`, keyed to the user's US-person, ITAR-authorisation and citizenship fields |
| 3.1.4 | Separate duties of individuals | ✅ | Segregation-of-duties permissions (CAPA verification, RCA review, disposition and step-override approval, supplier and part approval) are in the QA Manager and Tenant Admin presets only. Self-approval needs the template to allow it (or, for a CAPA plan, no other eligible approver) and a written justification, and is recorded as `self_approved`; `self_verified` records a CAPA or RCA verified by its own conductor |
| 3.1.5 | Employ principle of least privilege | ✅ | Presets grant per role. The Customer role sees only its own orders and what hangs off them, answers approval requests sent to it, and can invite viewers to its own orders |
| 3.1.6 | Use non-privileged accounts | ✅ | Floor roles (Operator, Receiving, Shipping) carry no administrative permissions; user management, classification and approval authority are separate groups |
| 3.1.7 | Prevent non-privileged users from executing privileged functions | ✅ | Group membership and permissions change only for holders of `change_tenantgroup`; approvals check the approver's eligibility on the request (`can_approve()`), and every change lands in the audit log |
| 3.1.8 | Limit unsuccessful logon attempts | ⚠️ | Sign-in is rate-limited per client IP (`THROTTLE_LOGIN`, default 10 a minute); signing passwords are throttled per user. No per-account sign-in lockout — with SSO, the identity provider's |
| 3.1.10 / 3.1.11 | Session lock; terminate session | ⚠️ | Sessions expire after `SESSION_COOKIE_AGE` of inactivity, optionally at browser close; API tokens expire after `API_TOKEN_TTL_SECONDS` (default one hour). No pattern-hiding screen lock. Set the lifetime as described in [CMMC](cmmc.md#identification-authentication-ia) |
| 3.1.22 | Control CUI posted on public systems | ✅ | Classification and export-control filtering govern what a Customer-role user can retrieve |

uqmes shows no system-use notice at sign-in (3.1.9).

## 3.3 Audit and Accountability

| Control | Requirement | | Implementation |
|---------|-------------|---|----------------|
| 3.3.1 | Create audit records | ✅ | `AuditlogMiddleware` + `AUDITLOG_INCLUDE_ALL_MODELS = True`, group permission and membership changes included; access records for document views and downloads, report generation, data exports and AI queries (`services/core/access_log.py`) |
| 3.3.2 | Ensure actions traced to individuals | ✅ | Every record carries its actor and a server timestamp. Approval responses record the signer, `verification_method`, `self_approved` and the trusted client IP; change records store the same trusted client IP |
| 3.3.4 | Alert on audit logging failure | ⚠️ **gap** | A failed access-record write logs at ERROR to `compliance.access_control` with the `audit_write_failed` marker. Nothing pages anyone until you route that marker — see [CMMC](cmmc.md#audit-accountability-au) |
| 3.3.6 | Audit reduction and report generation | ✅ | **Admin** > **Audit Log** and `/api/auditlog/` filter by actor, record type, record and action, with search and ordering; the filtered view exports to Excel or CSV behind `export_auditlog`, and each export is itself logged |
| 3.3.7 | Authoritative time source for timestamps | ✅ | Server-set, stored in UTC |
| 3.3.8 | Protect audit information | ✅ | PostgreSQL triggers refuse UPDATE and DELETE on six audit tables, superusers included; approval responses admit only withdraw, delegate, or answer again after withdrawal (`setup_audit_triggers`, run by `setup_database`) |
| 3.3.9 | Limit audit management to privileged users | ✅ | Browsing the trail needs `view_auditlog` (Tenant Admin, Document Controller, QA Manager, Auditor presets); one record's history needs `view_logentry` and access to the record. The endpoint is read-only |

## 3.5 Identification and Authentication

| Control | Requirement | | Implementation |
|---------|-------------|---|----------------|
| 3.5.1 | Identify users, processes, devices | ✅ | One account per person, signed in by email; API tokens belong to a user |
| 3.5.2 | Authenticate users, processes, devices | ✅ | Session (password or Microsoft SSO through django-allauth) or an expiring API token |
| 3.5.3 | Multifactor authentication | ⚠️ | Only through SSO with MFA enforced at the identity provider |
| 3.5.4 | Replay-resistant authentication | ⚠️ | Server-side sessions with CSRF tokens; the OIDC flow when SSO is used |
| 3.5.6 | Disable identifiers after inactivity | ⚠️ | Accounts are deactivated (singly or in bulk), never deleted; nothing does so automatically on inactivity |
| 3.5.7 / 3.5.8 | Password complexity; reuse | ⚠️ | Django's four validators (attribute similarity, minimum length, common passwords, all-numeric); no password history |
| 3.5.10 | Store and transmit only protected passwords | ✅ | Salted PBKDF2-SHA256 hashes, Django's default hasher |
| 3.5.11 | Obscure feedback of authentication info | ✅ | A failed sign-in does not say whether the account exists |

Signatures re-authenticate: an approval through the API needs a drawn
signature and the approver's password, and signing passwords are throttled
(five failures per gate, ten across gates, per user per 15 minutes). See
[Electronic Signatures](signatures.md).

## 3.13 System and Communications Protection

| Control | Requirement | | Implementation |
|---------|-------------|---|----------------|
| 3.13.2 | Employ architectural designs | ✅ | Tenant isolation in the application (tenant-scoped managers, tenant-membership checks at authentication). Database row-level security beneath it is opt-in with `ENABLE_RLS=true` |
| 3.13.3 | Separate user from system functionality | ✅ | The Django admin is a separate interface, open to superuser and staff accounts only |
| 3.13.4 | Prevent unauthorized data transfer | ✅ | `perform_update()` refuses changing a record's tenant; tenant-scoped querysets |
| 3.13.8 | Protect CUI in transmission | ⚠️ | With `DEBUG` off, session and CSRF cookies are marked Secure and HSTS is sent; TLS terminates at your proxy or platform |
| 3.13.15 | Protect authenticity of communications | ✅ | CSRF protection with a trusted-origin list; CORS allow-list |

!!! note "Row-level security is a setting"
    With `ENABLE_RLS=true`, `setup_rls` (run by `setup_database`) applies
    `FORCE ROW LEVEL SECURITY` and a tenant policy to the tenant-scoped tables
    it lists, and each request sets its tenant before it runs; a request whose
    tenant cannot be set is refused. With it off — the default — isolation
    rests on the application layer alone. PostgreSQL does not apply RLS to
    superusers, so the application must connect as a non-superuser role for
    it to bind.

uqmes encrypts stored integration credentials only; do not cite
application-layer encryption for CUI at rest (3.13.16).

## Organisation and hosting responsibilities

These are not the software's job, and uqmes does not perform or schedule them:

- **Your organisation:** security awareness training (3.2), incident response
  planning and reporting (3.6), personnel screening and offboarding (3.9),
  physical protection (3.10), risk assessment (3.11), security assessment, the
  SSP and the POA&M (3.12), external-system inventory (3.1.20), and reviewing
  logged events (3.3.3).
- **Your identity provider:** multifactor authentication, password history,
  account lockout and lifecycle, where you use SSO.
- **Your hosting:** remote, wireless and mobile access (3.1.12–3.1.19, 3.1.21),
  encryption at rest and TLS, network boundary and segmentation, host
  hardening, least functionality and software allow-listing (3.4.6–3.4.9),
  maintenance (3.7), flaw remediation and malicious-code protection (3.14),
  backups, clock synchronisation, and sanitising storage at disposal (3.8.3 —
  soft delete *retains* records on purpose and is not evidence for it).

**One application-level gap remains until you route it: 3.3.4** — see above.
