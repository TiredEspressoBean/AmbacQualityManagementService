# IATF 16949 — Clause Support

Which IATF 16949 automotive additions uqmes performs, and — more importantly here — which it does not yet.

## Overview

IATF 16949 builds on ISO 9001 with automotive-specific requirements,
particularly the AIAG Core Tools. See [ISO 9001](iso9001.md) for the base clauses
and for how the markers below are used.

!!! info "A second edition is coming, but not yet"
    IATF Global Oversight confirmed in July 2026 that a **second edition** is in
    development, with publication planned for **mid-2027** and transition aligned to
    ISO 9001. **IATF 16949:2016 remains current**, and this page maps it.

    The stated priorities are simplification, software quality assurance, supply
    chain management, launch management and customer-specific requirements. Software
    quality assurance is the one to watch here, since it is the first time the
    standard addresses it directly.

There is no readiness percentage here, but there is a plain answer about scope:
**uqmes implements only part of the AIAG Core Tools.** SPC is present and strong,
and control-plan data is captured per step. PPAP is present as an **approval
state** — a part approval per part type and supplier — and FMEA, MSA, PSW and AAR
exist as **document types** you file against, but none of them is modelled as
structured data. That is a
roadmap position rather than a scope boundary — unlike the management clauses,
these are things a quality system is expected to hold.

## SPC Implementation

The system provides comprehensive SPC capabilities:

| Feature | Implementation |
|---------|----------------|
| Chart types | X̄-R (subgroups 2-8), X̄-S (subgroups 9+), I-MR (individuals) |
| Capability indices | Cp, Cpk, Pp, Ppk |
| Control limits | 3σ limits, auto-calculated |
| Baseline management | Freeze/update with audit trail, `superseded_reason` |
| Out-of-control rules | Western Electric rules (8 rules) |
| Specification limits | From MeasurementDefinition (USL, LSL, nominal) |

**Key files**: `Tracker/models/spc.py` (SPCBaseline, SPCDataPoint)

## Control Plan Support

Control plan data is captured via `StepMeasurementRequirement`:

| Field | Purpose |
|-------|---------|
| `measurement` | Links to the measurement definition |
| `step` | Process step |
| `sequence` | Display / collection order |
| `is_mandatory` | Must be recorded to advance the step |
| `characteristic_number` | Balloon number on the drawing |
| `tolerance_upper_override` / `tolerance_lower_override` | Step-specific tolerances |
| `substep` | Optional link to the capturing substep |

**Key files**: `Tracker/models/mes_lite.py` (StepMeasurementRequirement)

    Whether a supplier is approved to produce a part type, on a PPAP basis, is
    a first-class record with a lifecycle and a receiving gate — see [Part
    Approvals](../workflows/supply/part-approvals.md). What is filed behind that
    approval is documents.

## Special Characteristics

!!! warning "Not implemented"
    There is no special-characteristic classification field. A measurement
    requirement can carry a `characteristic_number` — the balloon number from
    the drawing — but nothing marks a characteristic as Critical or
    Significant, and nothing keys behaviour off such a marking.

    The related controls are available individually and can be applied by hand
    to the characteristics that need them:

    - `is_mandatory` on the measurement requirement forces recording before the
      step can advance
    - SPC monitoring is configured per measurement
    - Substeps can be flagged **safety-critical**, which shows them to the
      operator as critical — see
      [Authoring Work Instructions](../workflows/dwi/authoring.md)

    There is no first-class Critical / Significant classification that applies
    these automatically.

## Rework Control

Per clause 8.7.1.4, rework is controlled:

| Feature | Implementation |
|---------|----------------|
| Visit counting | `QuarantineDisposition.rework_attempt_at_step` records which attempt a rework is |
| Maximum visits | `Steps.max_visits` limits rework attempts |
| Rework routing | Disposition workflow routes to rework step |
| Re-inspection | Required after rework completion |
